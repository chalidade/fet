# Deep Dive: Cara Kerja V8

> Terkait: [04 JavaScript](../roadmap/04-javascript.md), [16 Performance](../roadmap/16-performance.md).
> Deep dive lain: [Event Loop](event-loop.md), [Efisiensi di React](react-efficiency.md)

## Pertanyaan pembuka

JavaScript itu "diinterpretasi" atau "dikompilasi"? Kenapa fungsi yang sama bisa berjalan 10x
lebih cepat setelah dipanggil ribuan kali, lalu tiba-tiba melambat lagi? Kenapa urutan penulisan
properti object (`{ x, y }` vs `{ y, x }`) bisa memengaruhi performa, dan kenapa `delete obj.key`
sering disebut buruk?

## Model mental

V8 (mesin JS di Chrome, Node.js, Deno, dan Edge) adalah **kompiler bertingkat yang berspekulasi**.
Kode mulai berjalan secepat mungkin dengan cara yang murah, lalu bagian yang sering dipakai
dikompilasi ulang dengan asumsi dari apa yang sudah terlihat. Kalau asumsinya salah, kode kembali
ke tingkat bawah.

```
source ──► Parser ──► AST ──► Ignition (bytecode, interpreter)
                                 │  mengumpulkan feedback: tipe & bentuk object yang lewat
                                 ▼
                              Sparkplug (baseline, kompilasi cepat tanpa optimasi)
                                 ▼
                              Maglev (optimasi menengah, kompilasi cepat)
                                 ▼
                              TurboFan (optimasi penuh, berdasarkan feedback)
                                 │
                 asumsi gagal ◄──┘  deoptimization: kembali ke bytecode
```

Kuncinya ada di **feedback**. TurboFan tidak tahu tipe dari kode sumber, karena JavaScript tidak
punya tipe statis. Ia menebak dari apa yang benar-benar lewat saat Ignition berjalan. Kode yang
"bentuk datanya" konsisten mudah ditebak. Kode yang bentuknya berubah-ubah memaksa V8 terus
memeriksa atau menyerah.

## Mekanisme detail

### 1. Parsing yang malas

Mem-parse seluruh file mahal, padahal banyak fungsi tidak pernah dipanggil. V8 memakai
**pre-parser**: fungsi di dalam file hanya dicek sintaksnya dan dicatat batasnya. Parse penuh
(membuat AST dan bytecode) baru dilakukan saat fungsi pertama kali dipanggil.

Akibat praktisnya: fungsi yang langsung dipanggil (IIFE) bisa ter-parse dua kali kalau V8 tidak
mengenalinya sejak awal. Ini salah satu alasan bundler dan V8 punya heuristik khusus untuk pola
`(function () { ... })()`.

### 2. Ignition: bytecode dan feedback vector

Ignition mengubah AST menjadi **bytecode** untuk mesin register dengan satu *accumulator*. Kamu
bisa melihatnya sendiri:

```bash
node --print-bytecode --print-bytecode-filter=add -e "function add(a, b) { return a + b } add(1, 2)"
```

Hasilnya kurang lebih:

```
Ldar a1          ; muat b ke accumulator
Add a0, [0]      ; accumulator = a + accumulator, catat feedback di slot [0]
Return
```

`[0]` adalah slot di **feedback vector** milik fungsi itu. Setiap kali `Add` berjalan, V8
mencatat tipe yang terlihat: selalu small integer? kadang double? kadang string? Catatan inilah
yang nanti dipakai compiler optimasi.

### 3. Hidden classes (Maps)

Object JS terlihat seperti hash map, tapi menyimpan setiap object sebagai hash map itu lambat. V8
memberi setiap object sebuah **hidden class** (di source V8 disebut *Map*) yang mencatat properti
apa saja yang dimiliki dan di **offset** mana nilainya disimpan.

```js
const a = {};      // Map M0: (kosong)
a.x = 1;           // transisi M0 → M1: x di offset 0
a.y = 2;           // transisi M1 → M2: x@0, y@1

const b = {};
b.x = 5;           // memakai ulang transisi M0 → M1
b.y = 6;           // dan M1 → M2: a dan b berbagi Map yang sama
```

Object yang dibuat dengan properti yang sama **dalam urutan yang sama** berbagi Map. Kalau
urutannya berbeda (`b.y` dulu, baru `b.x`), V8 membuat rantai transisi baru dan kedua object
punya Map berbeda, walaupun isinya sama.

`delete obj.x` biasanya membuat object keluar dari model ini dan pindah ke **dictionary mode**
(hash map sungguhan): fleksibel, tapi akses propertinya jauh lebih lambat dan tidak bisa
dioptimasi dengan cara di bawah.

### 4. Inline caches

Akses `obj.x` di sebuah baris kode punya **inline cache (IC)** yang mengingat Map yang pernah
lewat dan offset `x` untuk Map itu.

| Status IC | Artinya | Biaya |
| --- | --- | --- |
| Monomorphic | Hanya satu Map yang pernah lewat | Paling cepat: cek Map, ambil dari offset |
| Polymorphic | 2–4 Map berbeda | Cek beberapa Map berurutan |
| Megamorphic | Lebih dari 4 Map | Jatuh ke lookup umum yang lambat |

Fungsi seperti `getX(p) { return p.x }` yang menerima object dari puluhan "bentuk" berbeda akan
megamorphic, walaupun semua object itu punya properti `x`.

### 5. Elements kinds

Array punya kategori sendiri untuk isinya, disebut *elements kind*, dari yang paling spesifik:

```
PACKED_SMI_ELEMENTS     [1, 2, 3]           integer kecil
PACKED_DOUBLE_ELEMENTS  [1, 2, 3.5]         ada angka desimal
PACKED_ELEMENTS         [1, 2, "a"]         campuran / object
HOLEY_*                 [1, , 3] atau new Array(3) yang belum diisi
```

Transisinya **hanya satu arah**, ke yang lebih umum. Setelah array menjadi `PACKED_ELEMENTS` atau
`HOLEY`, ia tidak akan kembali walaupun isinya diperbaiki. Array holey butuh pengecekan tambahan
karena "lubang" berarti V8 harus melihat ke prototype chain.

### 6. Optimasi spekulatif dan deoptimization

Saat fungsi cukup "panas", Maglev atau TurboFan membuat kode mesin berdasarkan feedback. Kalau
feedback bilang `a + b` selalu small integer, kode mesinnya cukup menjumlahkan dua integer, plus
**guard**: "kalau ternyata bukan integer, keluar".

Saat guard gagal, terjadi **deoptimization**: V8 membuang kode optimasi itu, menyusun ulang
state, dan melanjutkan di Ignition. Deopt sesekali tidak masalah. Yang mahal adalah siklus
optimasi → deopt → optimasi → deopt pada fungsi panas, karena tipe datanya terus berubah.

## Eksperimen

Jalankan dengan Node.js. `--allow-natives-syntax` mengaktifkan fungsi internal V8 seperti
`%HasFastProperties`. Ini hanya untuk eksperimen, jangan dipakai di kode produksi.

1. **Lihat bytecode.** Jalankan perintah `--print-bytecode` di atas untuk fungsi `add`. Ganti
   isinya dengan `a.x + b.x` dan perhatikan instruksi `GetNamedProperty` beserta slot feedback-nya.
2. **Hidden class bersama.** Simpan sebagai `maps.js`:
   ```js
   const a = { x: 1, y: 2 };
   const b = { x: 3, y: 4 };
   const c = { y: 4, x: 3 };
   console.log(%HaveSameMap(a, b), %HaveSameMap(a, c));
   ```
   Jalankan `node --allow-natives-syntax maps.js`. Jelaskan kenapa hasilnya `true false`.
3. **Dictionary mode.** Buat object dengan 3 properti, cek `%HasFastProperties(obj)`, lalu
   `delete` satu properti dan cek lagi.
4. **Deopt.** Buat fungsi `add(a, b)`, panggil 100.000 kali dengan integer, lalu sekali dengan
   string. Jalankan dengan `node --trace-opt --trace-deopt` dan cari baris yang menyebut `add`.
   Catat alasan deopt yang dilaporkan.
5. **Polymorphic vs monomorphic.** Ukur `getX(p)` yang dipanggil 10 juta kali dengan object satu
   bentuk, lalu dengan object dari 8 bentuk berbeda (`{x}`, `{x, a}`, `{x, b}`, …). Bandingkan
   waktunya dengan `performance.now()`.
6. **Elements kind.** Mulai dari `[1, 2, 3]`, tambahkan `1.5`, lalu `"a"`, dan cek setiap langkah
   dengan `%DebugPrint(arr)` (cari baris `elements kind`).

Catat hasil dan kejutannya di [catatan eksperimen](/notes/). Angka di eksperimen 5 berbeda di
setiap mesin. Yang penting adalah perbandingannya, bukan angkanya.

## Implikasi praktis

- **Inisialisasi semua properti di constructor atau literal**, dalam urutan yang sama, daripada
  menambahkannya belakangan secara kondisional. Class membantu karena bentuknya konsisten.
- Hindari `delete` di object yang sering diakses. Set ke `undefined`/`null`, atau gunakan `Map`
  untuk data yang kuncinya memang dinamis.
- Jaga array tetap homogen dan tanpa lubang: hindari `new Array(n)` yang diisi acak, dan jangan
  mencampur angka dengan string.
- Fungsi panas sebaiknya menerima tipe yang konsisten. Fungsi yang sengaja generik (misalnya
  utilitas `get(obj, path)`) wajar megamorphic, jadi jangan menaruhnya di jalur paling panas.
- Jangan mengoptimasi berdasarkan tebakan. Ukur dengan profiler (DevTools Performance,
  `node --cpu-prof`), lalu pakai `--trace-deopt` untuk mencari tahu kenapa fungsi panas tidak
  tetap teroptimasi.
- Detail tier (Sparkplug, Maglev, TurboFan) berubah dari versi ke versi, dan tidak semua tier aktif
  di setiap runtime. Di Node 22, `--trace-opt` biasanya langsung melaporkan target `TURBOFAN`. Prinsipnya tetap:
  **bentuk data yang stabil** mudah dioptimasi.

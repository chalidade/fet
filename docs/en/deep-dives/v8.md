# Deep Dive: How V8 Works

> Related: [04 JavaScript](../roadmap/04-javascript.md), [16 Performance](../roadmap/16-performance.md).
> Other deep dives: [Event Loop](event-loop.md), [Efficiency in React](react-efficiency.md)

## Opening questions

Is JavaScript "interpreted" or "compiled"? Why can the same function run 10x faster after being
called thousands of times, then suddenly slow down again? Why can the order you write properties
(`{ x, y }` vs `{ y, x }`) affect performance, and why is `delete obj.key` often called bad?

## Mental model

V8 (the JS engine in Chrome, Node.js, Deno, and Edge) is a **tiered, speculative compiler**. Code
starts running as quickly as possible in a cheap way, then hot code is recompiled using assumptions
based on what has already been observed. When an assumption turns out wrong, the code drops back to
a lower tier.

```
source ──► Parser ──► AST ──► Ignition (bytecode, interpreter)
                                 │  collects feedback: types & object shapes seen
                                 ▼
                              Sparkplug (baseline, fast compile, no optimization)
                                 ▼
                              Maglev (mid-tier optimizing, fast compile)
                                 ▼
                              TurboFan (fully optimizing, based on feedback)
                                 │
            assumption fails ◄──┘  deoptimization: back to bytecode
```

The key is **feedback**. TurboFan can't know types from the source, because JavaScript has no
static types. It guesses from what actually flowed through while Ignition was running. Code whose
"data shapes" are consistent is easy to predict. Code whose shapes keep changing forces V8 to keep
checking, or to give up.

## Detailed mechanism

### 1. Lazy parsing

Fully parsing a whole file is expensive, and many functions are never called. V8 uses a
**pre-parser**: inner functions are only syntax-checked and their boundaries recorded. Full
parsing (building the AST and bytecode) happens when a function is first called.

The practical consequence: an immediately invoked function (IIFE) can be parsed twice if V8
doesn't recognize it up front. That's one reason bundlers and V8 have special heuristics for the
`(function () { ... })()` pattern.

### 2. Ignition: bytecode and the feedback vector

Ignition turns the AST into **bytecode** for a register machine with a single *accumulator*. You
can see it yourself:

```bash
node --print-bytecode --print-bytecode-filter=add -e "function add(a, b) { return a + b } add(1, 2)"
```

The output is roughly:

```
Ldar a1          ; load b into the accumulator
Add a0, [0]      ; accumulator = a + accumulator, record feedback in slot [0]
Return
```

`[0]` is a slot in that function's **feedback vector**. Each time `Add` runs, V8 records the types
it saw: always small integers? sometimes doubles? sometimes strings? These records are what the
optimizing compilers use later.

### 3. Hidden classes (Maps)

JS objects look like hash maps, but storing every object as a real hash map is slow. V8 gives each
object a **hidden class** (called a *Map* in V8's source) that records which properties it has and
at which **offset** each value is stored.

```js
const a = {};      // Map M0: (empty)
a.x = 1;           // transition M0 → M1: x at offset 0
a.y = 2;           // transition M1 → M2: x@0, y@1

const b = {};
b.x = 5;           // reuses transition M0 → M1
b.y = 6;           // and M1 → M2: a and b share the same Map
```

Objects created with the same properties **in the same order** share a Map. If the order differs
(`b.y` first, then `b.x`), V8 builds a new transition chain and the two objects have different
Maps, even though their contents are the same.

`delete obj.x` usually moves the object out of this model and into **dictionary mode** (a real
hash map): flexible, but property access is much slower and can't be optimized the way described
below.

### 4. Inline caches

A property access `obj.x` at a given line has an **inline cache (IC)** that remembers which Maps it
has seen and the offset of `x` for each.

| IC state | Meaning | Cost |
| --- | --- | --- |
| Monomorphic | Only one Map seen | Fastest: check the Map, load from the offset |
| Polymorphic | 2–4 different Maps | Check several Maps in turn |
| Megamorphic | More than 4 Maps | Falls back to a slow generic lookup |

A function like `getX(p) { return p.x }` that receives objects of dozens of different "shapes"
becomes megamorphic, even though all of those objects have an `x` property.

### 5. Elements kinds

Arrays have their own category for their contents, called the *elements kind*, from most to least
specific:

```
PACKED_SMI_ELEMENTS     [1, 2, 3]           small integers
PACKED_DOUBLE_ELEMENTS  [1, 2, 3.5]         contains a decimal number
PACKED_ELEMENTS         [1, 2, "a"]         mixed / objects
HOLEY_*                 [1, , 3] or a new Array(3) not yet filled
```

Transitions go **one way only**, toward more general kinds. Once an array becomes
`PACKED_ELEMENTS` or `HOLEY`, it never goes back, even if you fix its contents. Holey arrays need
extra checks because a "hole" means V8 has to look up the prototype chain.

### 6. Speculative optimization and deoptimization

When a function is "hot" enough, Maglev or TurboFan generates machine code from the feedback. If
the feedback says `a + b` is always small integers, the machine code just adds two integers, plus a
**guard**: "if this isn't an integer after all, bail out".

When a guard fails, **deoptimization** happens: V8 throws away the optimized code, reconstructs the
state, and continues in Ignition. An occasional deopt is fine. What's expensive is a hot function
that keeps cycling optimize → deopt → optimize → deopt because its data types keep changing.

## Experiments

Run these with Node.js. `--allow-natives-syntax` enables V8 internals such as
`%HasFastProperties`. Use it only for experiments, never in production code.

1. **Look at the bytecode.** Run the `--print-bytecode` command above for `add`. Change the body to
   `a.x + b.x` and look for the `GetNamedProperty` instructions and their feedback slots.
2. **Shared hidden classes.** Save as `maps.js`:
   ```js
   const a = { x: 1, y: 2 };
   const b = { x: 3, y: 4 };
   const c = { y: 4, x: 3 };
   console.log(%HaveSameMap(a, b), %HaveSameMap(a, c));
   ```
   Run `node --allow-natives-syntax maps.js`. Explain why the result is `true false`.
3. **Dictionary mode.** Create an object with 3 properties, check `%HasFastProperties(obj)`, then
   `delete` one property and check again.
4. **Deopt.** Write `add(a, b)`, call it 100,000 times with integers, then once with strings. Run
   with `node --trace-opt --trace-deopt` and look for lines mentioning `add`. Note the deopt reason
   it reports.
5. **Polymorphic vs monomorphic.** Time `getX(p)` called 10 million times with objects of one
   shape, then with objects of 8 different shapes (`{x}`, `{x, a}`, `{x, b}`, …). Compare the times
   using `performance.now()`.
6. **Elements kind.** Start with `[1, 2, 3]`, add `1.5`, then `"a"`, and check each step with
   `%DebugPrint(arr)` (look for the `elements kind` line).

Record your results and surprises in your [experiment notes](/en/notes/). The numbers in
experiment 5 differ between machines. What matters is the comparison, not the absolute numbers.

## Practical implications

- **Initialize all properties in the constructor or literal**, in the same order, instead of adding
  them conditionally later. Classes help because their shape is consistent.
- Avoid `delete` on objects that are accessed often. Set to `undefined`/`null`, or use a `Map` for
  data whose keys really are dynamic.
- Keep arrays homogeneous and without holes: avoid `new Array(n)` filled out of order, and don't mix
  numbers with strings.
- Hot functions should receive consistent types. Intentionally generic functions (such as a
  `get(obj, path)` utility) are naturally megamorphic, so keep them off the hottest paths.
- Don't optimize on guesses. Measure with a profiler (DevTools Performance, `node --cpu-prof`), then
  use `--trace-deopt` to find out why a hot function doesn't stay optimized.
- Tier details (Sparkplug, Maglev, TurboFan) change between versions, and not every tier is enabled
  in every runtime. In Node 22, `--trace-opt` usually reports a `TURBOFAN` target directly. The
  principle stays the same: **stable data shapes** are easy to optimize.
